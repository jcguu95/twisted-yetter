This protocol is local-store tooling for the CTL Meta dogfood shadow store. It
does not change =ctl-kernel/1=, =ProjectStateRoot=, =AdmissionBatch=, canonical
encoding, authority, or CID semantics.

* Problem

When two Git worktrees both admit CTL transitions, Git sees JSON conflicts, but
CTL cares about semantic state:

- current root;
- logical id bindings;
- active revision CID;
- recorded revision reachability;
- transition parent roots;
- admission manifest reachability.

Therefore =refs/main.json= must not be resolved by choosing ours/theirs. It is a
current-root pointer. The normal semantic resolution is to create a new child
root on top of the target current root.

* Commands

Dry-run a semantic root merge:

#+begin_src sh
cd ctl-dogfood
python3 scripts/ctl_merge.py merge-root \
  --incoming-store-root /path/to/other/ctl-dogfood \
  --format text
#+end_src

Admit a no-conflict transplant:

#+begin_src sh
cd ctl-dogfood
python3 scripts/ctl_merge.py transplant-revisions \
  --incoming-store-root /path/to/other/ctl-dogfood \
  --expected-root "$(python3 -c 'import json, subprocess; print(json.loads(subprocess.check_output(["python3", "scripts/ctl_store.py", "current-root"]))["root_cid"])')" \
  --admitted-at 2026-07-06T00:00:00Z \
  --format text
#+end_src

The legacy aliases =preview= and =admit= remain available, but
=merge-root= and =transplant-revisions= are the preferred names.

* Operator Runbook

Use this when Git reports conflicts in =ctl-dogfood/refs/main.json= or
under =ctl-dogfood/objects/= after two worktrees both admitted CTL state.

1. Keep the target worktree on the branch that should receive the merged CTL
   state.

2. Do not choose Git ours/theirs for =refs/main.json=. Leave Git conflict
   resolution aside and ask CTL what the roots mean.

3. Run a dry-run from the target =ctl-dogfood= directory:

   #+begin_src sh
   python3 scripts/ctl_merge.py merge-root \
     --incoming-store-root /path/to/incoming/ctl-dogfood \
     --format text
   #+end_src

4. Read the text report:

   - =status: ok= means the incoming CTL transitions can be represented on top
     of the target current root.
   - =status: conflict= means at least one =logical_id= needs a profile-owned
     semantic decision before a full transplant.
   - =summary= counts =auto-admit=, =already-present=, and =conflict= binding
     operations.
   - =logical ids= is the human-facing list to inspect first.
   - =warnings= may report incoming branch-local manifests that should not be
     copied as target-current sidecars.
   - for automation, rerun with =--format json= to get =logical_ids[]= and
     =items[]=.

5. If =status= is =conflict=:

   - inspect =conflicts[]= or =logical_ids[]=;
   - use the listed =logical_id=, active CID, incoming CID, and =payload_diff=;
   - if the report also has =auto-admit= items, the text output may show an
     optional =--auto-only= partial transplant command;
   - =--auto-only= only applies safe binding operations and leaves conflicting
     active bindings untouched;
   - admit an explicit resolution or correction revision for the remaining
     conflicts by the profile's own rules;
   - rerun =merge-root=.

6. If =status= is =ok=, transplant:

   #+begin_src sh
   python3 scripts/ctl_merge.py transplant-revisions \
     --incoming-store-root /path/to/incoming/ctl-dogfood \
     --expected-root "$(python3 -c 'import json, subprocess; print(json.loads(subprocess.check_output(["python3", "scripts/ctl_store.py", "current-root"]))["root_cid"])')" \
     --admitted-at 2026-07-07T01:00:00Z \
     --format text
   #+end_src

7. Verify:

   #+begin_src sh
   python3 scripts/verify.py
   #+end_src

8. Commit the resulting object files, =refs/main.json=, and generated manifest
   together.

* What Downstream Must Provide

The generic upstream tool needs only CTL store roots and objects:

- target =ctl-dogfood= directory;
- incoming =ctl-dogfood= directory;
- optionally explicit =--main-root=, =--incoming-root=, or =--base-root= CIDs.

Downstream does not need to explain its ontology to this tool. If the report
says =conflict=, downstream must decide the semantic resolution because only the
profile owner knows what a combined or corrective revision should mean.

** Scope Check

Before accepting any branch-store merge feature, verify:

- it only depends on CTL roots, revisions, bindings, transition batches,
  manifests, refs, or filesystem-local store shape;
- it does not inspect domain-specific payload fields to decide semantic
  correctness;
- it does not generate a combined payload or choose a semantic winner;
- it does not require auditing a downstream repository;
- it preserves =ctl-kernel/1= semantics.

If any answer fails, the feature belongs to a profile-owned or downstream-owned
tool, not this upstream dogfood layer.

For a simple no-conflict import, expect:

logical ids:
  - claim:example: auto-admit

    --admitted-at <UTC> \

#+end_example

For a mixed report with safe and conflicting logical ids, expect an optional
partial transplant command:

#+begin_example

logical ids:
  - claim:safe: auto-admit
  - claim:example: conflict
    main: ctlobj-sha256:...
    incoming: ctlobj-sha256:...
    payload: changed

  python3 scripts/ctl_merge.py transplant-revisions \

    --admitted-at <UTC> \
    --auto-only \
    --format text
#+end_example

The operator should resolve the =logical_id= conflict, not the file conflict.

* Merge Model

The tool:

1. loads objects from the target and incoming stores;
2. validates both roots against the target trust anchor;
3. finds or accepts a base root;
4. walks incoming transitions after the base root;
5. reports each binding operation by =logical_id=;
6. classifies each operation as =auto-admit=, =already-present=, or =conflict=;
7. for no-conflict transplants, re-admits the incoming revisions as new
   single-parent child roots on top of the target root;
8. for =--auto-only=, re-admits only =auto-admit= binding operations and
   records skipped conflicts;
9. warns about incoming branch-local manifest sidecars that should not become
   target-current manifests;
10. rewrites =refs/main.json= to the new child root;
11. writes a =ctl-dogfood/merge-manifest/1= manifest.

* Conflict Report

The dry-run report is logical-id first. A conflict means the target active
binding is not the incoming expected CID, not the incoming result CID, and not a
later state on the incoming logical-id path.

For bound-vs-bound conflicts, the report includes:

- target active revision CID;
- incoming revision CID;
- revision kind and payload profile;
- parent CIDs;
- a top-level payload diff.

This is intentionally more useful than a Git conflict on individual JSON files:
the operator should see the affected =logical_id=, not merely a filename.

* Dependency Ordering

The dogfood merge tool preserves incoming transition order and validates every
generated admission batch with the reference kernel validator.

Profile-specific payload dependency ordering, such as profile-owned endpoint
dependencies, remains =backlog=. In =ctl-kernel/1=, =parents= only describe
same-logical-object revision lineage; arbitrary cross-object dependencies
belong to profile-defined payload references. A future ResearchCTL or
downstream profile tool can add dependency extraction without changing this
kernel-level transplant model.

* Unsupported

- multi-parent =ProjectStateRoot=;
- automatic combined conflict revision generation;
- profile-specific endpoint dependency sorting;
- payload-aware merge policy beyond top-level conflict diff.

These are intentionally not hidden behind the generic merge command.
